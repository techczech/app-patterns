# `@app-patterns/vault-sync`

Automatic backup for a Git-versioned folder of documents. The engine takes snapshots of the files you name, pushes them to a backup branch on the configured remote and checks that the remote holds them. It records how long the oldest edit has gone without a verified backup, so an app can warn when that age passes its limit.

The engine never changes the user's Git state. It does not touch HEAD, the index, staged changes or any file in the worktree, so it can run while people or other tools commit in the same repository.

This package is the core engine plus a foreground helper spike (`@app-patterns/vault-sync/helper`, below). It has no user interface, installed background service or sign-in support.

## Use

```ts
import { createBackupEngine } from "@app-patterns/vault-sync";

const engine = createBackupEngine({ machineId: "studio-mac", remote: "origin", trustedCredentialHelpers: ["osxkeychain"] });
const scope = { include: ["chapters", "notes/**/*.md"], exclude: ["notes/drafts"] };

// When the user edits a document, report the edit for that document and keep its ticket.
// It counts as unprotected until that document's save is acknowledged and backed up.
const ticket = await engine.noteEdit(vaultPath, editTime, { path: "notes/chapter-1.md" });

// When the editor saves in place: announce the write first, acknowledge it once the bytes are durable,
// naming the document and the newest ticket the saved bytes contain.
const writeToken = await engine.noteWriteStart(vaultPath, ["notes/chapter-1.md"]);
// ... write and fsync ...
await engine.noteFlush(vaultPath, {
  upTo: newestTicketInThisSave,
  paths: ["notes/chapter-1.md"],
  completedWrites: [{ path: "notes/chapter-1.md", token: writeToken }],
});

// On the backup cadence (for example once a minute):
const snapshot = await engine.capture(vaultPath, scope);
const pushed = await engine.pushBackup(vaultPath);
if (pushed.state === "pushed" || pushed.state === "up-to-date") await engine.verify(vaultPath);

const { protectionAgeSeconds, lastError, pending } = await engine.status(vaultPath);
```

## Behaviour

- **Snapshots.** `capture` builds a commit with Git plumbing and a private index kept in the checkout's git directory (`<git-dir>/vault-sync/`). It starts from the previous snapshot, applies the added, changed and removed paths in scope, and makes a commit when the tree changed or an initial empty scoped snapshot is needed to carry exact absence proof. A genuinely empty scope with no such proof creates no snapshot; later unchanged captures reuse the existing snapshot. The only parent is the previous snapshot. The user's commits are never parents, so a push publishes only content that was in scope when it was captured, never the repository's history.
- **Existing backup history.** Before a chain is extended or pushed, every commit in it must be a snapshot this engine made for this machine and checkout, descending from a root commit the engine recorded when it made it (`<git-dir>/vault-sync/chain.json`). A chain from an older version (whose snapshots had the user's HEAD as a parent) or anything else under the backup branch stops backup with the block reason `unsupported-history`. Nothing is rewritten or deleted.
- **Coverage record.** Each snapshot's commit message carries `snapshot-format: 2`, `coverage-through: <ms>` (every edit made before that time was on disk and is in the snapshot, except in the pending files and unlisted folders), `pending-files: <n>` and `unlisted-folders: <n>`. `listBackups` reports these as `protectedThrough`, `pendingFiles` (files and folders together; 0 only for a complete capture) and `unlistedFolders`, with `coverage: "unknown"` for a tip without them. The commit time is reported separately as `snapshotTime` and is not a coverage claim.
- **Scope.** Only paths matching an include pattern and no exclude pattern are captured. A pattern without wildcards names a file or a whole directory; `*` and `?` match within one path segment and `**` spans segments. `.git` and nested repositories are never captured. File bytes are stored as they are on disk; Git filters are not applied.
- **Stable reads.** A file is read only after its last change is at least `settleMs` old (default 250 ms), and the read is accepted only if size, times and inode are unchanged afterwards. A file that does not settle after the bounded retries is left at its previous snapshot version and reported in `pending`. A file in a folder that exists but cannot be read is also left pending, never recorded as deleted, and the folder itself is reported as pending (`unlisted`), because files that were never captured may be in it. A path is recorded as deleted only after a direct check finds it gone, including an acknowledged path that disappeared before its first snapshot. Its absence must be in scope, accessible without symlinked ancestors and free of coordinated writes during the check. An unchanged snapshot can cover that absence after verification.
- **Capture recovery.** A request makes at most three complete passes under the same operation lock, waiting 100 ms between passes only when a file was left `writing` or `unstable`. Fresh record generations and all existing safety checks apply to each pass. A monotonic two-second budget, measured from the first pass, limits retry read work and waits; checks run between filesystem operations and during settling waits. An in-flight filesystem or Git call must return before a budget check can run. A pass admitted to commit finishes its existing ref/record writes without a budget interruption. The first pass always completes normally. Earlier safe partial snapshots remain in the same chain. The returned snapshot, `startedAt`, changes and pending paths describe the last completed pass; `startedAt` is that pass's start, and `committed` reports whether that pass made a commit. Capture and retry do not resolve protection age; the corresponding snapshot still needs push and exact remote verification.
- **Writer contract.** Stable reads reject a write that is visibly in progress, but they cannot prove a write is complete: a writer that pauses mid-write for longer than `settleMs` leaves bytes that look settled. A writer is supported when it either replaces files atomically (writes a temporary file, then renames it over the target) or calls `noteWriteStart(paths)` before writing in place and `noteFlush` after the bytes are durable, supplying the returned token for each completed path in `completedWrites`. Only an exact path/token match ends an active interval; old receipts and acknowledgements without tokens leave it active, including all-document acknowledgements. Replaying a completed receipt is safe. Starts that overlap an active path are refused, so writers must serialise their intervals on that path. Atomic replacements need no write token. Between those calls the engine keeps the paths at their previous snapshot version, and so does any capture that was reading while such a write started or finished. Other writers that change files in place are not supported.
- **Backup branches.** Snapshots go to `refs/heads/backup/<machine-id>/<checkout-id>/<yyyy-mm-dd>` (UTC). The checkout id is created once per checkout and kept in the engine folder. Each day's branch starts from the previous day's last snapshot, so the chain is continuous.
- **Backup remote.** The remote must have exactly one address, used for both pushing and fetching, and that address must be HTTPS, a `file://` address or an absolute local path. SSH addresses, remote helpers and remotes that set `receivepack`, `uploadpack`, `vcs` or `mirror` are refused with the block reason `unsupported-remote`. Push, verification, the secret scan and restore all use this one remote.
- **Push and verify.** Before every push the engine scans every blob reachable from the snapshot it sends: the whole chain, each time, because the remote can drop anything it held between any listing and the push. A chain whose blobs together exceed `maxScanTotalBytes` is held back (`too-large-to-scan`), so the scan's cost grows with the chain. `pushBackup` then makes a normal push of the newest backup branch. A rejected push is reported as `rejected` and never retried with force. `verify` reads the remote branch with `git ls-remote`; only the pushed object id counts as verified.
- **Network transport.** Each push, verification and restore fetch checks the remote once at its start and then uses that address, not the remote's name, in a private Git directory the engine creates for the operation and removes afterwards. No repository, user or system Git configuration applies there, so a change to the remote during a scan, an address rewrite (`url.*.insteadOf`), a protocol grant or a TLS setting such as `http.sslVerify=false` in the repository has no effect. HTTPS trust and credentials come only from the application: its environment (for example `GIT_SSL_CAINFO` for a private certificate authority), its `gitEnv` and its `trustedCredentialHelpers`.
- **Deadline record.** `<git-dir>/vault-sync/deadline.json` holds every edit not yet in a verified snapshot, the last verified snapshot and the protected-through time. Order comes from the record's own generation counter, never from clock readings; times only measure age. An edit reported with `noteEdit` stays unprotected until a `noteFlush` naming its path (or all documents) and a ticket at least its own acknowledges its save, a capture that read the record after the acknowledgement reads the saved file or confirms it deleted, and that snapshot is verified. An edit reported without a path is covered only by an acknowledgement with `allDocuments: true` followed by a complete capture. Changes the engine finds on disk without a report are protected once the capture that read them is verified; a file or folder it cannot read counts as unprotected from the capture before. Restarts, failed pushes, failed checks and elapsed time never resolve an edit. A record of an older schema, or a damaged one, is set aside and replaced by one that keeps its oldest known edit time (or the file's last write, if earlier) as one unsaved edit of unknown documents, which only an all-documents acknowledgement and a later verified complete capture clear.
- **Git processes.** Git runs from argument arrays without a shell, with time and output limits; an abort signal stops the process group. Inherited `GIT_*` variables that could point Git at another repository or index are dropped. Repository hooks, the file-system monitor, automatic maintenance and signature checks are switched off for the engine's own Git calls, and replacement refs and grafts are ignored. Only the file and HTTPS transports are allowed (`GIT_ALLOW_PROTOCOL`, which no configuration can widen), the far-side programs are fixed (`--receive-pack`, `--upload-pack`), and the repository's credential helpers and askpass program are cleared; the only credential helpers that run are those passed as `trustedCredentialHelpers`. `status` lists the repository's hooks that the engine does not run. Commits are not signed.
- **Concurrency.** Operations on one checkout are serialised inside a process and across processes by a lock in the engine folder. A lock left by a process that has exited is reclaimed by removing only that process's own lock file, so two processes recovering at once cannot both take it. Edit and save reports use a separate short lock and do not wait for a capture, push or verification.

## Foreground helper (spike)

`src/helper/` runs the engine on a schedule for explicitly registered vaults and answers `status` and `syncNow` over a local Unix socket. It is a foreground process with a required runtime bound. It installs nothing: no launch agent, login item, daemon or scheduled job, and there is no command that would create one.

```sh
bun src/helper/cli.ts run --config /abs/helper.json --runtime-dir /abs/rt --max-runtime-ms 600000
bun src/helper/cli.ts status --runtime-dir /abs/rt [--vault notes]
bun src/helper/cli.ts sync-now --runtime-dir /abs/rt --vault notes
```

```json
{ "configVersion": 1, "machineId": "studio-mac", "captureIntervalMs": 60000,
  "vaults": [{ "id": "notes", "path": "/abs/vault", "include": ["notes"], "exclude": [], "remote": "origin" }] }
```

- **Registration.** Only the vaults in the configuration file are backed up; nothing is discovered. The file must be a regular file owned by the user and not writable by group or others. Registration is not enablement: each vault also needs the engine's own `enable`, done separately. The helper never enables a vault, so an unenabled vault reports `not-enabled`.
- **One engine per vault.** Each vault gets its own engine instance with every engine guard in force. A failure in one vault does not affect another. A local folder or `file://` remote counts as private; any other address counts as visibility unknown, so its pushes stay held back until a later stage adds a real visibility check and credentials.
- **Cycles.** A cycle is capture, push, then verify. At most one cycle runs per vault, and no timer is armed while it runs. The cadence is absolute (`start + k × interval` on the wall clock). After a late wake, or a cycle that took longer than the interval, the helper waits for the next future slot and skips the missed ones, never a burst. Timers are at most 5 s long, so a wall-clock jump is noticed within 5 s, and a monotonic fallback keeps the cadence if the wall clock goes backwards. `syncNow` during a cycle waits for one follow-up cycle that starts after the request.
- **Outcomes.** `verified` means exact remote verification of the snapshot that cycle captured. Guard refusals are `blocked` with the engine's block. Failures are `capture-failed`, `push-failed` or `verify-failed`, and a stop gives `cancelled`.
- **Status.** Each answer reads the engine's status for that request, bounded by a 2 s timeout. A timeout or error gives `summary: "unknown"`, `fresh: false` and the last known engine status. The best summary is `no-known-unprotected-edits`, which is deliberately not "protected": until app adapters report edits, edits made after the last capture are unknown. `uncertainty` lists the reasons. Over the socket, each path list (pending files, unlisted folders, files being written, hooks not run, secret findings, unscanned blobs) is sent as `{ count, items, omitted }`: the exact count, up to 100 entries, and the number left out. If a reply would still exceed 1 MiB the sample shrinks to 10 entries, then to none. The summary, uncertainty and every count are computed from the full status first and are never shortened.
- **Socket.** The runtime folder must be a real folder owned by the user with mode 0700; the helper creates it if missing but never changes an existing one. Its path may not contain `.` or `..` segments. The helper and the client resolve it to its real path and use that one folder for the checks, the socket and the owner lock, and they confirm it is still the same folder before removing a stale socket and after binding. The socket is mode 0600. Node has no peer-credential check, so the folder's permissions keep other users out, and the client refuses a socket in a folder that fails the same check. One helper owns a runtime folder at a time, and each vault is claimed by one helper in its engine folder (`<git-dir>/vault-sync/helper-owner`), so two helpers with different runtime folders still cannot both schedule a vault. Both claims use the engine's cross-process folder lock, held for the helper's whole life. A live owner is never displaced, and a helper that finds any claim taken refuses to start. A dead owner's socket is replaced, but a non-socket file in its place is left alone and refused. On shutdown the socket is removed only if it is still the one this process created.
- **Protocol 1.** The protocol is newline-delimited JSON. A connection must start with `{"type":"hello","protocol":1,"client":"…"}`, and any other version is refused with `protocol-mismatch`. Requests are `{"id":n,"method":"status","vault"?:id}` and `{"id":n,"method":"syncNow","vault":id}`. Requests name vaults only by registered id. Paths, scopes, remotes and commands cannot be sent. A request with an unknown field is refused with `bad-request` for that request, and the connection stays open; extra hello fields are ignored. Request lines are limited to 64 KiB and reply lines to 1 MiB, with 16 connections and 8 queued requests per connection. The client checks every reply in full: a hello for another protocol version, a reply with another request's id, an unknown field or a line nobody asked for closes the connection and fails the request. A connection that fails while connecting is always closed. `noteEdit`, `noteWriteStart` and `noteFlush` are answered `not-available` in protocol 1. Receipts travel only on a protocol-2 connection (below); a protocol-1 connection answers exactly as it did before protocol 2 existed, apart from the helper version.
- **Protocol 2 (receipts lane).** A separate connection that starts with the strict receipts hello (exactly `type`, `protocol: 2`, `lane: "receipts"`, `client`, `clientId`, `clientEpoch`, `writer` and `capabilities: ["receipts-2"]`) carries `openStream`, `noteEdit`, `noteWriteStart`, `noteFlush`, `noteWriteAbandon`, `adopt` and `receiptStatus`. The helper answers with engine level 1 and its version. Each request is checked for its exact fields before anything else. It names a registered vault, and every path must be inside that vault's registered scope (`out-of-scope` otherwise); a request cannot carry a folder, scope, remote, attestation or process proof. The helper passes each request to that vault engine's receipt API with the registered path, and checks again after its last wait before each engine call that this path is still its own real path, so a folder replaced meanwhile is refused (`activation-refused`); the engine resolves the path once more itself, after that check. That API uses the short record lock and never the operation lock, so a running cycle or a held `syncNow` does not delay a receipt. The helper attests receipt activation, sends receipts and releases write guards only while it holds its runtime-folder claim and every vault claim and is not stopping, checked again immediately before each such engine call. It takes over from a previously activated helper only on that helper's exact sealed shutdown report, or when no process with that helper's process id exists on this host; a process with that id is never taken as gone, whatever start time it reports, because that start time follows the wall clock. Anything uncertain is refused. Before a `receiptStatus` it releases only those write guards of this client's earlier writer processes that are observed gone the same way. Nothing is retried: a request whose reply is lost is `outcome-unknown`, and the caller resends the identical request with the same seq. Shutdown waits for receipt requests in progress before it releases the claims. `connectReceipts` (exported from `./helper`) is the client: it assigns no seqs, keeps at most 8 requests waiting, and checks every reply field against the request it sent, using copies taken when the connection and each call were made. Status replies must name this connection's epoch, give each row the state the engine's precedence gives it and use one object-id length. Each call's timeout and cancellation count from the call, time spent waiting in the queue included: one that ends before its request is written is `not-sent`, one that ends after closes the connection. It needs helper 0.2.0 or later; an older helper refuses the hello, and receipts are then unavailable.
- **Shutdown.** SIGINT, SIGTERM, SIGHUP or the runtime bound stops accepting requests and lets running cycles finish for up to 20 s (`--shutdown-grace-ms`). After that it cancels them through the engine's abort signal. The claims on the runtime folder and the vaults are released only after every cycle and status read has actually ended and every process the helper started is gone. A start that fails part-way stops whatever it had started in the same way before it releases them. The command line protects itself from SIGINT, SIGTERM and SIGHUP from before the start begins until the run has ended: the first signal asks for a stop (at once, or as soon as the start completes), and later ones are reported and ignored.
- **Process ownership.** Every Git and secret-scanner process the helper's engines start is launched through the helper's process registry, which starts it in a process group of its own and records that group before the launch returns. A group stays recorded until no process is left in it, even after the command itself has closed, so a process the command left behind is still owned whoever its parent now is. On a normal stop, once every cycle has ended, no new process may start and anything left in a recorded group is killed and confirmed gone before the claims are released. A process that moves itself out of its group is not covered by this record; the programs launched are Git, with hooks, maintenance and credential helpers disabled, and gitleaks, and neither does so in the engine's use.
- **Bounded stop.** `stop()` answers within the grace period plus a hard stop period (15 s, `--hard-stop-ms`). It answers `stopped` when everything has ended, the socket is removed and the claims are released. A socket that is already gone, or that another file has replaced (left in place), does not prevent `stopped`; a socket or claim file that cannot be removed does. It answers `overdue` when work ignored cancellation; the claims then stay held until that work ends. It answers `failed` when a shutdown step itself failed, with what was established: whether the work ended, what became of the socket, and whether the claims were released. A failing step never releases a claim early: the claims stay held until the work is known to have ended, and a failed attempt to end the helper's processes is retried. A start that fails part-way, or is refused while lookup processes are still running, answers within the same bound and reports `overdue` or `failed` the same way. An error from the socket server while the helper runs is a fault: it stops the helper through the same steps and the answer is `failed` once the work has ended, with the claims released only then. The event stream ends with `stopped` only for a helper that started; a failed start's clean cleanup ends with `start-cleaned-up`, and the command exits 2 for it, also when its work ended only after containment had begun. After `overdue` or `failed` the command line ends the process itself. It refuses new processes, kills every recorded process group and, using the process list as a supplement, every other descendant and the groups they lead; it exits with code 3, without releasing its claims, only once a check finds none of them left. The claims become reclaimable once the process has gone, which is after every writer has stopped. A Git command killed this way can leave a Git lock file behind. If a child survives being killed, or the process list cannot be read, nothing is confirmed: the command keeps running and keeps its claims, and tries again. Further signals during shutdown are ignored, so a second Ctrl-C cannot skip these steps. An outside SIGKILL, or a blocked event loop, is beyond this bound and can leave child processes running.

Not covered by the spike: installation as a login service, behaviour across a real sleep and wake, a two-hour run, HTTPS visibility and credentials, app adapters, the receipts lane under a running helper's full lifecycle, and Windows.
